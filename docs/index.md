# FoPost Provider

Manage [FoPost](https://fopost.com) as infrastructure: workspaces, labels, webhooks, and automations. Posts are deliberately not managed here — see the provider guide below.

## Example Usage

```terraform
terraform {
  required_providers {
    fopost = {
      source  = "fopost/fopost"
      version = "~> 0.1"
    }
  }
}

# With no arguments the provider reads FOPOST_API_KEY from the environment,
# which keeps the key out of the configuration and out of version control.
provider "fopost" {}
```

## Authentication

The provider authenticates with a FoPost API key, created in the dashboard under
**Settings → API Keys**. Supply it in either of two ways:

- Export `FOPOST_API_KEY` before running Terraform. This is the recommended way — a key
  written into a `.tf` file is a key committed to version control.
- Set the `api_key` argument on the `provider` block, from a variable your secret store
  fills in.

The key's scopes decide what the provider can do. A key without the scope a resource needs
fails with a permission error naming the scope, not a silent no-op.

`FOPOST_BASE_URL` overrides the API root. Leave it unset unless you are pointing at a
non-production FoPost deployment.

## What This Provider Manages, and What It Does Not

Terraform is for durable configuration — objects with a stable identity that should keep
existing until you say otherwise. That is what this provider models:

| Object | Why it belongs in Terraform |
| --- | --- |
| `fopost_workspace` | The tenant boundary. Long-lived, and everything else hangs off it. |
| `fopost_label` | Campaign taxonomy. Long-lived, and worth keeping identical across environments. |
| `fopost_webhook` | An integration contract with a system you also operate. |
| `fopost_automation` | A rule that keeps running. Reviewing a change to it in a pull request is exactly the point. |

**Posts are deliberately not a resource.** A published post is an event, not a piece of
infrastructure. Modelling one as a resource would mean Terraform trying to "update" content
that is already live on a social network, and destroying it — deleting real posts — the
moment the block leaves the configuration. Create posts through the
[FoPost API](https://fopost.com/docs), the SDKs, or the dashboard.

**Connected accounts are read, never created.** Connecting an account is an interactive
OAuth handshake with the platform, so the `fopost_account` and `fopost_accounts` data
sources read what the dashboard connected.

## Drift and Deletion

Every resource reconciles a 404 by removing itself from state, so an object deleted in the
FoPost dashboard is planned for re-creation rather than failing the run. Attributes the API
assigns — identifiers, timestamps, run counters — are read back on every refresh.

Two secrets are issued exactly once, at creation: `fopost_webhook.secret` and the
`fopost_automation.secret` of an `api_webhook` trigger. The API never re-issues them, so an
**imported** subscription or automation has no secret in state. Both are marked sensitive.

## Local Development

Before this provider is published, and whenever you are testing a change to it, point
Terraform at a locally built binary with a `dev_overrides` block in `~/.terraformrc`:

```hcl
provider_installation {
  dev_overrides {
    "fopost/fopost" = "/path/to/your/GOBIN"
  }

  direct {}
}
```

Then `go install .` and run Terraform as usual. Do **not** run `terraform init` with
`dev_overrides` in place — Terraform reads the override and warns that it is skipping
installation, which is the expected behaviour.
